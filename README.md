V4 adds explicit provider-local key provisioning and public enrollment proofs. Start with [the enrollment runbook](docs/PROVIDER_ENROLLMENT.md). The existing v3 hosted Space refuses startup until real all-three enrollment is complete; this is expected. No production authority is granted.

# ARDA post-quantum quorum — isolated candidate v3

Version 3 adds real GitHub ML-DSA-65 and HF SLH-DSA-SHA2-192s signing components, a bounded authenticated HF HTTP adapter, operator-pinned configuration loaders and disabled deployment templates. Read `docs/PROVIDER_WITNESSES.md` for custody, source-check and hosting boundaries. The v2 R13 gate and review-leaf reservation component remain; their historical notes are in `docs/R13_AND_RELEASE_LEDGER.md`.

This package implements a three-of-three review quorum using real post-quantum signatures. It does not install a release, enroll a signer, deploy a provider, publish to Rekor or grant production/execution authority. Generation 14 remains sealed and unsigned.

## Verify on Debian

Extract into a fresh directory and run without sudo:

```bash
python3 tools/host_preflight.py &&
python3 run_verification.py
```

Requirements: Python 3.10+, cryptography, PyYAML, Node.js with node:sqlite support, a C compiler, make, OpenSSL 3.5+ with ML-DSA-65 and SLH-DSA-SHA2-192s, and OpenSSL development headers/library (`libssl-dev` on Debian). The preflight reports actual algorithm availability. If either algorithm is missing, stop and return that report; the runner does not install or replace system cryptographic libraries.

The runner verifies vendor source hashes, builds local binaries, runs upstream HSS/LMS test vectors, then runs 94 PQ/R13/provider Python tests, 8 source Python tests and 21 Node tests. Expected: all suites PASS, TESTS=123, PRODUCTION_AUTHORIZED=FALSE. Build warnings about the unmodified upstream OpenSSL SHA256 API are retained in VERIFICATION_RESULT.json. This is not a FIPS module-validation or independent cryptographic audit claim.

Tests use disposable keys. HSS private state remains in a temporary test process's RAM and is destroyed on exit; test signing code is never deployed. ML-DSA/SLH-DSA fixture keys live only in a private temporary directory, removed afterward. The test runner makes no provider calls.

## Fixed witness allocation

| Provider | Enrolled role | Required signature |
|---|---|---|
| GitHub | build_witness | ML-DSA-65 |
| Hugging Face | policy_witness | SLH-DSA-SHA2-192s |
| Cloudflare release witness | release_witness | HSS/LMS SHA256 N32 H10 W8, one level |

Every identity, role, public key, algorithm and parameter set is pinned by a trusted enrollment policy. All three must sign the same proposal digest and enrollment-policy digest. No threshold reduction, Ed25519 fallback, KEM-as-signature substitution, unknown witnesses, duplicate votes or alternate parameter sets are accepted. This is three different signature schemes, with lattice and hash-based mathematical assumptions; the two hash-based schemes are not claimed to have independent underlying assumptions.

Cloudflare's release witness and its existing R13 verifier are separate roles. The live Cloudflare HSS signer is NOT implemented. Before enrolling it, its signing state must be protected against concurrency, crash, fork, cloning, exhaustion and backup rollback. H10 has 1024 one-time leaves; rotation must be approved before exhaustion. A receiver-side leaf ledger can detect observed reuse; it cannot prevent signer-side reuse or replace secure signer-state management.

## Proposal and replay boundaries

Votes bind the witness/provider/role, exact algorithm/key digest, policy digest, proposal digest, decision and timestamps. Proposals bind the actual machine/boot, generation, manifest, complete deployment digest, artifact-root digest, request digest, R13-evidence digest, policy epoch, nonce, intended action and expiry. Validity is at most five minutes. `review_staged_release` is the only accepted action.

`ReviewJournal` atomically consumes the nonce, certificate digest and HSS leaf into a FULL-synchronous private SQLite database. Concurrent attempts yield one review intent. Consumption survives process restart and SIGKILL after commit. A failure before commit leaves no partial intent. The journal refuses observed policy/clock rollback and a clock rollback between verification and commit. It is not an external rollback-resistant monotonic store; production recovery must protect the ledger and trusted time separately. The journal needs a separate controller identity and owner-only storage.

`verify_quorum()` can report `quorum_valid: true`, while `decision` remains REFUSE, `production_authorized` remains false and the interlock stays closed. `ReviewJournal.consume()` stores REVIEW_INTENT only. Neither method invokes a loader, executor or completion API. `tools/check_certificate.py` additionally requires an operator-supplied enrollment-file hash; it always exits nonzero because production admission is unavailable.

## Generation-14 review draft

The reviewed host request is preserved at `inputs/generation14-staging-request.json`. Its exact bytes are pinned in the proposal preparer. A draft is included at `inputs/GENERATION14_REVIEW_DRAFT.json`. It is explicitly UNREADY_DRAFT: enrollment, fresh R13 evidence, provider signatures, signer-state review and Rekor proof are missing. Its null binding fields are rejected by the quorum verifier. Do not sign or treat this draft as ready.

To create a fresh unsigned draft from your original host request:

```bash
python3 tools/prepare_review.py \
  --request "$HOME/arda-campaign-d-generation14-staging-request.json" \
  --out "$HOME/arda-pq-review-draft.json"
```

The output uses exclusive creation and refuses an existing file. Draft creation changes no ARDA state. Adding this verifier to the measured runtime will require a later staged release; this package does not edit the sealed generation-14 files.

## Rekor and fresh R13 evidence

`public_commitment(certificate)` produces only a schema identifier and certificate digest. It is a minimal logging payload, not a transparency proof. This version neither uploads it nor verifies Rekor inclusion/checkpoints. A supported Sigstore outer envelope and full proof verification must be integrated before admission can pass. A Rekor receipt never counts as a fourth approval.

The v2 R13 gate can independently verify a supplied fresh capture, including the raw quote and signed receipt, against pinned keys and an independently approved baseline. No fresh real-host capture has been exercised through that gate here. The original `verify_quorum()` remains signatures-only; callers needing attestation must use `verify_with_r13()`. No `r13_verified` or `rekor_verified` boolean is accepted as authority. Rekor proof verification remains unimplemented.

Existing TPM, R13, GitHub identity/provenance and public transparency infrastructure retain their own algorithms and trust roots. This package proves the three PQ approval-signature paths; it does not claim the entire machine-attestation/transparency chain is post-quantum.

## Source and remaining work

OpenSSL supplies the ML-DSA and SLH-DSA primitives. The HSS/LMS verifier uses unmodified Cisco `hash-sigs` sources with exact upstream Git blob hashes and tree identity in `vendor/UPSTREAM.json`; its license is included. The production-facing native wrapper links only the verification library. Stateful signing is confined to disposable tests.

Next required deployment work: enroll actual provider identities/public keys with explicit operator pins; build and validate the supplied provider images and hosted signing paths; establish secure HSS state custody; integrate actual Sigstore/Rekor proof verification and validate the new R13 gate with fresh host evidence; add the verifier to a new measured release; then wire the exact action-specific admission consumer and installer/recovery path. None of these gates is marked complete by the local test results.
